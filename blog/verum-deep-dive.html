Verum: an outreach agent that's only allowed to send what it can prove

Sep 2026·8 min read
Claude agents MCP Scheduled routines SPF / DKIM / DMARC
Landing page ↗

Most "AI outreach" tools are email generators wearing a sales pitch. You give them a company name, they invent a personalized-sounding paragraph, and you send it and hope. I didn't want to build that, mostly because I'd have to use it on my own company first, and I didn't want to be the one getting the fabricated-sounding email.

Verum is what I built instead: an agent that researches a company from primary sources, and is structurally incapable of sending an email unless every claim in it traces back to a source URL and every gate passes. If it can't prove something, it doesn't get to say it.

Not a generator. An operator.

The distinction sounds like semantics until you build it. A generator stops at "write me a cold email." An operator owns the whole loop: find the company, verify there's a real gap, find the right person, write to them, track the thread, follow up once, escalate a reply to me, and know when to stop. Most of the engineering effort is in the parts that aren't "write the email" — the email is the easy 10%.

Ranuvo, my own company, is customer zero. Dogfood it against real prospects, measure what I still had to do by hand, extract those manual steps into features, and only then think about turning it into a product for other people. Building the multi-tenant SaaS before knowing whether a single email gets a reply is the expensive way to find out it doesn't.

The pipeline

discover → verify → research → draft → REVIEW → send → track → follow up
                                 ▲                          │
                                 └──────── escalate ─────────┘

REVIEW is a human gate — me — and it's not a placeholder for a feature I haven't built yet. It stays there permanently for anything the agent scores as low confidence, even after the rest of the pipeline is trusted.

Finding the right person is the actual hard part. The agent doesn't look for "an email." It works out which function owns the problem it thinks it found — from leadership pages, filings, org structure — and treats absence as a signal too: no CIO on the executive page is why the target becomes finance instead of IT. Then it looks for a named individual, but only from sources it trusts enough to act on: a company's own leadership page or a filing is usable directly; a data broker or technographics site is a lead, never a confirmed contact, until something in tiers one through three backs it up.

Finding a route to that person follows the same rule. A published address on the company's own site, or a contact form — fine. Guessing firstname.lastname@company.com — never, under any circumstance, because a bounce from a guessed address costs domain reputation and a misdirected guess is worse. If no address can be verified, the record is marked blocked, not downgraded and sent anyway. Two of the first three companies worth writing to sat in exactly that blocked state, verified person, no verified way to reach them, and stayed there rather than getting a guessed send.

Eleven gates, and any one of them can kill a send

Before anything goes out, it has to clear all eleven: real fit for what Ranuvo actually sells, a sourced current problem (not an assumption), a dated reason to write now, a verified contact route, the right person, no pending acquisition or layoffs that make the timing wrong, never contacted before, not on the suppression list, no invented facts, an allowed country under that country's actual outreach law, and high confidence on every other gate — meaning if I had to argue for a gate rather than just confirm it, it doesn't count as passed.

If any gate is uncertain, the lead goes to REVIEW with the specific failing gate named next to it. That's a normal, expected outcome — not a failure of the run. On the first real batch of ten companies, three were disqualified once the agent worked out they'd already built the thing I would've pitched them. Pitching a company its own product is the fastest way to get ignored, and the agent found that out from public sources before a single email went out.

State lives in git, not memory

Runs happen as scheduled cloud jobs, not on my laptop, and each run starts from a completely fresh checkout with no memory of anything before it. So the first thing every run does is restore state from a dedicated git branch — pull it, check it out, and every send, every reply, every follow-up gets written back to that same branch and pushed before the run ends. If a run crashes mid-send, the next run reads exactly what happened, because it's committed, not held in a process that just died.

The actual safety net, though, is that the Sent folder itself is the source of truth on duplicates — not the state file. Immediately before every send, the agent searches Sent for that recipient's domain and cross-checks it against what the state file thinks happened. If they disagree, Sent wins, the state file gets corrected, and nothing gets sent to that company on that run. A crashed run can leave the state file wrong; it can't make the mailbox lie about what it already sent.

Replies end the agent's authority, not start it

A reply classified INTERESTED, HOT, or QUESTION gets a drafted response — and then it stops. It doesn't send. It flags for me. The only replies the agent acts on unattended are the mechanical ones: an out-of-office pushes the follow-up date, a "wrong person" referral updates the contact record. Anything with actual judgment in it — pricing, a commitment, ambiguity — waits for a human, because that's almost every real reply.

NOT_INTERESTED is the one exception that runs immediately and without waiting: straight to the suppression list, before anything else happens, no exceptions. An agent that keeps following up after someone says no is worse than no agent. That's not a compliance line I added for the readme — it's the actual design constraint the rest of the reply-handling logic is built around.

What it looks like from the outside

One digest a day, built from the state store rather than the mailbox, so it renders the same regardless of which provider is plugged in behind it:

NEEDS YOU (2)
  • Company A — draft ready, no verified contact. Blocked 3 days.
  • Company B — reply classified INTERESTED. Not auto-answered.

SENT (0) — sending disabled this run

FOLLOW-UPS DUE (1)
  • Company C — due, first follow-up

QUEUE
  2 CONTACT · 5 HOLD · 3 SKIP

Things that need a decision come first, on purpose, because the summary has to be readable on a phone in fifteen seconds, not read like a log file.

The landing page is the only part of this that's public. Everything above it — prospect research, contact records, the mailbox, the send log — stays in a private repo, because none of that should ever be something a link can accidentally expose.
